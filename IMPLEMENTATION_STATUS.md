# Nest Transport — Implementation Status

Last updated: 2026-10-09. Design reference: Nest Play (`sports-pixelate/frontend`). Stack: React+Vite+Tailwind (JSX) (same config/tokens as Nest Play), Express+Mongoose API (plain JavaScript, ES modules).

## Nest Play inspection findings (Phase 1)
- Web: Vite, React 18, **Tailwind 3 + shadcn/Radix**, lucide-react, recharts, TanStack Query, React Router 6, DM Sans.
- Look: **neo-brutalist** — 2px black borders, hard offset shadows (`nb-card`, `nb-btn`, `nb-badge`), primary `#024BAB`, accent `#FA731C`, sidebar 15.5rem / header 4rem, uppercase 12px table headers on `#024BAB/5`.
- Backend: plain-JS Express + Mongoose + JWT. Mobile: React Native 0.86 (`NestSports/`), lucide-react-native, React Navigation, `@react-native-community/geolocation`.
- Reused verbatim: `tailwind.config.ts`, `index.css` (tokens + nb-* utilities), `button/card/dialog/input/select/tabs/badge/StatCard/Toaster`, `AppLayout/AppSidebar/AppHeader` (adapted: nav, auth, brand; Nest Play notifications and trial banner removed).
- Deliberately not copied: Nest Play logos/branding (Nest Transport has its own wordmark).

## Done
- API: auth (register-org, login w/ lockout, refresh, logout invalidation, change-password), RBAC permission map, tenant scoping on every query, audit log, Zod validation, pagination, rate limiting, helmet/CORS.
- Vehicles: CRUD, registration validation + per-org uniqueness, filters/search, status rules, driver assign/unassign with two-sided consistency and availability checks, archive safeguards.
- Drivers/staff: CRUD, licence rules, status rules, archive safeguards.
- Dashboard: real counts + 30-day document expiry list (vehicle docs + driver licences) + empty state.
- Web: login/register, dashboard, vehicles, drivers/staff (list, search, filters, pagination, forms, confirm dialogs, loading/empty/error states).
- Routes & stops (Phase 3): Route model with embedded ordered stops, server-derived sequence, coordinate/time validation, per-org unique code, activate (needs 2 active stops), duplicate, archive (inactive only), `version` bump on edit for future trip snapshots, vehicle/driver refs checked in-org and for availability. Web: routes list + editor with Leaflet map (click to add stops, reorder, remove). Distance/duration are manual (no routing provider configured); map lines are straight, not road geometry.
- Trips & dispatch (Phase 4): Trip model with per-org numbering (TRP-00001), immutable route snapshot (route edits never change existing trips), server-side state machine (draft/scheduled/assigned/ready/in_progress/delayed/completed/cancelled/aborted; terminal states cannot be restarted), overlap detection for vehicle/driver/attendant (back-to-back allowed), availability + licence-expiry checks, vehicle on_trip/driver on_duty set at dispatch and released on completion/abort, reasons required for delay/cancel/abort, mid-trip vehicle/driver replacement, embedded status history, reschedule via edit. Recurring schedules: days-of-week, bounded generation (62 days), idempotent per (schedule,date) via unique key, conflicting days created unassigned and reported. Times converted using the organization's IANA timezone. Web: trips table, week calendar, create/edit, action dialogs, replace, detail with history, schedules tab, dashboard trip cards.
- Trip events & manifest (Phase 5): append-only TripEvent log (event time vs server receipt time, actor, source, stop, coordinates, notes); corrections add a new event pointing at the original, which is never modified; Passenger + PassengerAssignment models (pickup/drop stops validated against the route); manifest with live boarded/dropped/missing state derived from effective events; duplicate boarding/drop-off blocked; events only while trip is live; future/pre-start timestamps rejected; `clientId` idempotency for offline replay; system events for create/assign/start/delay/complete/cancel/abort; drivers/attendants limited to trips they are assigned to (Driver.user link) and cannot correct events. Web: Passengers page, trip detail tabs (Overview / Manifest / Events) with board/drop/missing buttons, incident entry and correction flow.
- GPS & live tracking (Phase 6): GpsDevice (hashed per-device keys, shown once, rotatable), provider adapter registry (generic JSON only), device ingestion endpoint with per-ping validation, duplicate/out-of-order handling, separate LocationPing history and VehiclePosition latest-fix collections, hourly retention purge, driver-phone ingestion limited to the driver's own active trip, Socket.IO with token auth and per-org rooms, live board API with server-computed freshness and trip/next-stop info, history trail. Web: live map (freshness-coloured markers, locally re-aged so silent vehicles turn stale), vehicle detail panel with last-update time and "last known" warning, filters, connection indicator, "no GPS source" banner, device management with one-time key reveal. See docs/GPS_INTEGRATION.md.
- Maintenance, fuel & expenses (Phase 7): Maintenance records (MNT-numbering, types, priority, parts, next-service date/odometer) with a status machine; starting work puts the vehicle Under Maintenance (so it can't be assigned to new trips), refuses if the vehicle is on a trip, lists upcoming trips affected; completing requires final cost, rejects a lower odometer, raises vehicle odometer, restores the vehicle only when no other work is open; cancelling releases it; service reminders by date/km. Fuel: server-computed/validated totals, odometer ordering vs neighbouring fills, duplicate and clientRef idempotency, measured efficiency only between consecutive full-tank fills (no estimates). Expenses: categories, pending→approved/rejected with reason, submitter cannot approve own, approved records locked, double-submit protection, cost summary counting only approved expenses + completed maintenance + fuel. Per-org `fuelExpenses` module switch (403 when off; rest of system unaffected). Dashboard: maintenance counts and (for roles that can read expenses) month costs. Web: Maintenance page, Fuel & Expenses page (Fuel / Expenses / Costs tabs).
- Documents & expiry (Phase 8): Document model for vehicle/driver/organization documents and attachments on expenses, maintenance and fuel; storage adapter (local disk, random keys, path-traversal guard, files never served statically; every download is an authenticated, org-scoped API call with nosniff/CSP-sandbox/no-store headers and an audit entry); uploads validated by file signature (PDF/JPEG/PNG/WebP only, 10 MB cap, client MIME/extension ignored), orphan cleanup on failure; per-owner-type permissions (e.g. drivers cannot read vehicle documents); verification workflow (changing dates/number/type/file resets to pending); expiry status always derived from dates (expired / expiring soon / valid / no expiry) with org-configurable reminder days; summary counts; archive instead of delete; expiry sync into vehicle/driver fields so dashboard alerts follow uploaded documents (newer expiry wins); `findReminderDue()` ready for the Phase 9 notification job (one bucket per threshold, dedupe key). Web: Documents page (cards double as filters, upload/edit/verify/archive, authenticated view/download), reminder-days setting, attachment dialogs for expense receipts and maintenance invoices.
- Notifications (Phase 9): in-app notifications (inbox, unread count, read/read-all, bell in header, realtime push to the user's socket room); event catalog with defaults and per-org overrides (enabled / channels / roles); editable plain-text templates; adapters for email (SMTP), SMS (Twilio), WhatsApp (Meta Cloud) and a not-implemented push stub; external channels need server credentials AND admin enablement (enabling an unconfigured one is rejected); DeliveryAttempt log with masked addresses, retry/backoff (1/5/30 min, then failed), "skipped" when unconfigured; dedupe keys; personal channel opt-outs; failures never affect the triggering operation; scheduled jobs for trips starting soon, document/licence expiry buckets and maintenance due. Triggers wired into trips (assigned/started/delayed/cancelled), breakdown reports and route edits. Web: bell dropdown, Notifications page (preferences, events & channels matrix, test sends, templates, delivery log). See docs/NOTIFICATIONS.md.
- Transport requests (Phase 10): TransportRequest model (REQ-numbering, 9 types, priority, effective date, related trip/route/vehicle/passenger, reviewer, resolution notes, status history). Types with automatic, validated effects: trip cancellation, vehicle/driver replacement, additional trip, schedule change, passenger route/stop assignment (add or remove), new stop (inserts in position, bumps route version, existing trips keep their snapshot), new route (created inactive for review); special requirements stay open for manual follow-up (approved → in progress → resolved). Rules: dangling references are rejected at filing; reviewers get a dry-run impact preview; approval re-validates against the CURRENT state, then claims the request atomically (two simultaneous approvals apply once — tested), then applies; a validation or apply failure changes nothing and leaves the request under review with the reason recorded; requesters cannot review their own request; rejection needs a reason; requesters see only their own requests; attachments on requests are visible only to the requester and reviewers (also excluded from bulk document listings). Notifications: reviewers on submit, requester on approve/reject. Dashboard shows requests awaiting review. Web: Requests page with type-driven form, Needs review / My requests / All tabs, detail with impact preview, history, attachments and review actions.
- Reports & CSV (Phase 11): 14 reports — daily and monthly trips, trips by route / vehicle / driver, route performance, delayed trips, cancelled trips, vehicle utilization, driver duty, maintenance, fuel consumption, vehicle expenses, document expiry — with date range (max 366 days, organization timezone, strict date validation), totals, explanatory notes, server pagination and CSV export (UTF-8 BOM, formula-injection neutralised, totals row, notes, audit-logged, no-store). Access: each report needs the matching permissions (e.g. fuel/expenses reports need expenses:read and the fuel module; dispatchers see operations + maintenance; accountants see cost reports; drivers see none); every query is organization-scoped. Data-honesty rules: on-time % and average late start are blank below 5 timed trips; "days used %" is blank for vehicles added during the period; hours exclude trips without recorded times; cost per km only when every completed trip has a distance; km per unit only between full-tank fills; unlinked expenses are called out. Efficiency calculation is shared with the fuel endpoint. Web: Reports page with report picker, range presets, chart for trip reports, totals row, notes, pagination and authenticated CSV download. The test suite found and fixed a bug where the driver-duty report returned unmapped rows.
- Settings, users & password reset (Phase 12): user management (create/edit/role/activate/deactivate, staff-profile linking one-to-one) with owner > admin > others hierarchy, no self role change or self deactivation, last-active-owner protection, sessions revoked immediately on deactivation or role change; accounts are created with an invitation link (single-use, hashed token, 7-day expiry) so no one ever knows another person's password; forgot-password (non-enumerating response, rate-limited, 60-minute single-use link, superseded by newer links, signs out all sessions and clears lockouts on use); admin-issued reset links; own profile, change password, sign out everywhere; organization settings (name, type, timezone validated, currency, GPS retention, module switches) with immediate effect; filterable tenant-scoped audit log viewer. Email for links goes out whenever SMTP is configured on the server; otherwise the admin gets the link to share. Web: Settings page (Organization / Users & roles / My account / Audit log), forgot- and reset-password pages.
- Fees & billing (Phase 13, optional module): fee plans (route / pickup stop / flat; monthly, term, one-time), passenger discounts and surcharges (fixed or %, period windows), invoice generation with preview and idempotency per passenger+period, manual invoices, adjustments with mandatory reasons and a floor at amount paid, void/regenerate, payments (partial, method-specific reference rules, overpayment and race protection, idempotent retries), refunds as separate capped records, reconciliation, outstanding balances with aging, receipts (printable), fee collection and outstanding-fees reports, audit entries for every financial change; money held as integer minor units. Razorpay: server-created orders, signature + direct payment lookup before recording, signed raw-body webhook, unique payment ids so verify/webhook/retries record once; secrets stay server-side. Web: Transport Fees page (Invoices, Outstanding, Payments, Fee plans & discounts), invoice detail with record payment / pay online / adjust / void / refund / receipt. See docs/BILLING.md.
- Mobile app + driver API (Phase 14): `mobile/` React Native 0.86 (JavaScript). Server: `/api/v1/driver/*` (me, my trips, ready, start, complete, emergency) built on a shared trip-transition service so web and phone obey identical rules; start window (60 min before to 12 h after), assigned-driver-only actions, idempotent replays; emergency event with configurable critical notification (default in-app/email/SMS to owner/admin/dispatcher); drivers/attendants can now read only their own trips, manifests and event logs on every endpoint. App: login with keychain token storage, silent refresh that never signs out on a network failure, cached trips/manifest/me for offline viewing, ordered offline queue for stop/boarding/report events with idempotency keys and a visible rejected-updates list, connection-required rules for start/finish, location sharing between start and finish (permission flow, foreground service, buffering and batch upload, visible status), trip screen with navigation, arrival marking, boarding/drop-off/missing, delay/breakdown/incident reports, emergency + call dispatch, management tabs (overview, trips, request review). Verified: 25 Jest tests (queue ordering/failure handling, API refresh/offline behaviour, start-window rules, ping buffering, screen smoke) and a Metro production bundle. NOT verified: native builds, device permission prompts, real background location. See mobile/README.md.

## Known limitations
- Mobile: never run on a physical device or emulator here; native build, permissions and background location are unverified; no push notifications; no parent/passenger app; offline start/finish deliberately unsupported; attendants cannot start or finish trips (driver only).
- Billing: Razorpay flows tested only with mocked HTTP/signatures (no sandbox account); refunds are recorded locally and not pushed to Razorpay; no GST/tax lines or sequential-by-financial-year invoice numbering; no automatic late fees or payment reminders; parents cannot pay themselves until the parent experience (Phase 14).
- Reports: no PDF export (CSV only); the transport fee collection report arrives with billing (Phase 13); list reports stop at 20,000 rows on screen / 50,000 in CSV and say so; reports are computed live from records (no caching), so very large organizations may want pre-aggregation later; fuel/trip "on-time" depends on drivers recording real start times.
- Requests: a person cannot review their own request or expense, so a single-user organization needs a second admin to approve; parent-submitted requests wait for the parent role (Phase 14); changes are applied with single-document writes (no multi-document transaction), mitigated by validate-then-claim-then-apply and revert-to-review on failure; replacements on live (in-progress) trips are dispatcher-only, not request-driven.
- Notifications: email/SMS/WhatsApp adapters have not been exercised against real providers; WhatsApp needs approved templates for business-initiated messages; push is not implemented; request approved/rejected notifications are wired in Phase 10. Header search box was removed because it was not connected to anything.
- Local-disk file storage only (no S3 adapter written yet); no virus scanning; back up the uploads directory with the database. Maintenance has no "authorized exception" to assign an in-workshop vehicle.
- GPS: no physical tracker or third-party fleet API has been connected; only the generic JSON adapter exists. Live tracking is unproven until a real source is observed end to end. ETA is not shown (no routing provider). Next stop is shown only if drivers record "stop reached" events.
- Email links need SMTP configured on the server; without it an administrator must pass links on by hand. Password reset is by emailed link only (no SMS/OTP).
- Passenger stop references use stop names; renaming a stop after assignments exist can orphan the stop match on the manifest.
- Trip start is not yet restricted by time-of-day or to the assigned driver; driver-only start comes with the mobile app (Phase 14). Trips keep an embedded status history in addition to the TripEvent log.
- Recurring generation is a manual, bounded action (no background auto-generation job).
- Web UI visuals have **not** been compared side-by-side with Nest Play in a browser yet; build and typecheck pass only.
- Refresh token is stored in localStorage (Nest Play convention); httpOnly cookie would be stronger.
- Forms use controlled state with server-side Zod validation; react-hook-form not yet used.
- Whole project is plain JavaScript (no TypeScript) by request; Nest Play web is TS, so copied components had types stripped.
- Local dev has no MongoDB installed: use `npm run dev:memory` (in-memory, data lost on exit).
- Sidebar only lists built modules.

## Run
API: `cd api && cp .env.example .env && npm run dev` (or `npm run dev:memory`), tests: `npm test`. Web: `cd web && npm run dev` (port 5175, proxies /api to 5100).
